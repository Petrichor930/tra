# Cmd

## 简单介绍：
1. 首先要说明的是Cmd只做数据处理,
在Extensions中创建设备实例,进行通信协议，中断回调的配置，原始数据的解析等，
再底层的就是bsp硬件层
所以, 从 底层硬件抽象层bsp 到 设备通信与协议层 再到数据处理与应用层 这是一个数据层层传递的过程。

2. 要想比较彻底理解如何控制的（比如问你怎么用遥控器控制电机？怎么获取遥控器原始数据，要对遥控器数据作什么处理？），
建议从bsp看起, 并注意以上三层层于层之间是怎么联系在一起的,
或者从cmd倒推其他两层的数据传输流程

3. 如果你搞明白这些, 应该可以自己写一套代码自行控制设备
至少会对调试有所帮助（比如解决接受不到数据的问题）

# 核心角色与定位
Cmd 处于应用层，它本身不直接处理底层硬件协议，而是：
    汇聚来自不同数据源（遥控器、上位机、裁判系统）的输入。
    处理这些输入，根据业务逻辑做出决策。
    分发控制指令给各个执行模块（底盘、云台等）。
这是一个典型的分层架构。(介绍已说过)

# 架构
[ 遥控器/上位机 ]  --(原始数据)--> [ Extensions (协议解析) ] --(事件)--> [ Cmd (决策中心) ] --(控制指令)--> [ 底盘/云台... ]

# 数据流总结
1. 中断：遥控器串口接收完成一帧数据。
2. Extensions：Rc 对象解析原始数据，设置 RC_READY_EVENT 事件。
3. Cmd：
    Cmd::task 检测到事件，调用 RcMsgHandler::handle()。
    handle() 方法读取并平滑摇杆数据。
    masterHandle() （业务逻辑） 将摇杆数据解算为 ChassisMsg_s 并发送。
4. 执行：底盘任务从队列中取出 ChassisMsg_s，驱动电机运动。

# 核心运行机制：事件驱动 + 消息总线
## 消息总线
    MsgBus_s 结构体是核心，它包含了通往不同执行模块（底盘、云台、机械臂、裁判系统）的 FreeRTOS 队列句柄。
## 事件驱动
    事件组：eventGroup_ 当底层数据准备好时（如串口接收完一帧数据），会设置对应的事件位。
    主循环：Cmd::task 在一个无限循环中等待任何事件发生。一旦有事件被触发，它就调用 parseMsg() 来查找是哪个数据源准备好了，并分发给对应的 Handler 去处理。
（设置事件位的核心目的，是让同一线程能高效处理多个等待任务，既避免线程因单个任务阻塞而 “卡死”，又能减少多线程带来的资源消耗。）

# example模块化与可扩展性（如何添加新的控制逻辑）
1. 定义消息：在 MsgImpl.hpp 中为新的功能定义消息结构体。
2. 扩展Handler：在对应的 Handler::handle() 方法中，添加解析逻辑并填充你的新消息。
3. 实现业务逻辑：在 masterHandle() 或专用的 xxxHandle() 方法中，编写决策逻辑，并使用 notify() 发送消息。
4. 创建消费者：确保有对应的模块任务在监听你的新消息队列并执行动作。
    （条件编译：通过 APP_USE_REFEREE 等宏定义，可以灵活地裁剪功能，适应不同的硬件配置或比赛要求。）
